# v6.10运行中启动v7：代码隔离与资源边界

日期：2026-10-27。结论：代码／结果／VTR可隔离地共存；能否同实例计算取决于v6.10阶段及剩余资源。这里没有读取服务器进程或负载，不能保证某个实例当前有余量。

## 先检查Git更新，不改活跃的2D源码

v6.10 `run.py::implementation()`冻结v6.10自身以及部分v6.8/v6.9源码哈希。本次3D提交不修改这些文件。但服务器可能尚未同步此前已存在的v6.10修复，不能只看本次提交就认定整次pull安全。

在原TailCompile仓库执行：

```bash
git fetch origin
git diff --name-only HEAD origin/main -- experiments/vtr \
  ':(exclude)experiments/vtr/tailcompile_v7_3d'
```

输出为空，表示本次更新没有其他2D／共享VTR脚本变化，此时可`git pull --ff-only`；仍应保留服务器本地修改，不能reset或强制覆盖。输出不为空则先保留活跃源码，不在运行中的v6.10上pull；需要另行安排同Git的固定执行视图或等该任务结束，不能将新旧源码混入同一个cohort。若服务器分支与远端分叉，ff-only会停止，需要单独处理。

## 阶段与资源

| v6.10状态 | v7建议 |
|---|---|
| 准备／综合／宽度扫描 | 有闲置CPU和足够内存／磁盘时，可低并发运行v7构建及prepare |
| 正式timing | 分开运行高负载任务，保持原计时协议；检查源码和阅读报告可以继续 |
| 状态未知／实例已满载 | 先检查状态与资源，不直接启动默认32并发 |

v6.10 `all`及就绪子集执行会自动进入timing，当前在准备不代表未来一直不计时。`taskset`只限制CPU核，不能隔离共享缓存、内存带宽和I/O。`nice`／`ionice`只是优先级，也不是资源预留或公平计时保证。若计时波已受新负载影响，保留原结果并在冻结的新timing_run中复测，不能与原负载混算。

v7资源探测依据affinity／CPU quota和当前内存余量，不会自动扣除v6.10正在使用的CPU。建议首次共存从单任务开始：

```bash
export TAILCOMPILE_3D_TRAIN_DEVICE=cpu
export TAILCOMPILE_V7_BUILD_JOBS=1
export TAILCOMPILE_V7_JOBS=1
export TAILCOMPILE_V7_RRG_JOBS=1
export TAILCOMPILE_3D_QUALIFICATION_JOBS=1
entry=experiments/vtr/tailcompile_v7_3d/prepare_server.sh
bash "$entry" --check
mkdir -p logs
log="logs/v7_prepare_$(date +%Y%m%d_%H%M%S).log"
nohup nice -n 10 bash "$entry" >"$log" 2>&1 </dev/null &
echo "PID=$! LOG=$log"
```

这些值不是服务器余量的证明；启动前检查`free -h`、`df -h .`及当前进程。可将v7绑定到确认闲置的物理核，但正式timing仍应与其他负载分开。默认入口只到prepare，不立即派发480或训练；首轮不需要GPU。

## 文件与环境隔离

原2D VTR只读；2026-10-28起新建3D后端在主仓库 `.deps/tailcompile_v7_3d/` 内，已建外部3D后端仅通过显式read-only模式核验／执行。v7输出、图、RRG和清理只限自己的cohort／scratch，不使用v6.10缓存。公开变量为3D／v7前缀，泛变量仅传子进程；TMPDIR／TMP／TEMP／XDG_CACHE_HOME指向v7专属scratch，避免继承2D临时目录。服务器不向主仓库和用户指定原VTR根以外新增写入。不要在运行中升级、安装或重建共用conda环境。

本次没有改变v6.10参数、结果、checkpoint、输入schema或原VTR binary；也没有在服务器代为启动／暂停任一任务。
